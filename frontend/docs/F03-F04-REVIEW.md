# AutoLog F03·F04 점검 결과

작성: 2026-11-14 · 근거 수준: Notion 작업 정의 확인 / 팀 Mock Fixture 실행 검증 / 로컬 브라우저 검증. 실제 SDK·실차·APK 검증 결과가 아닙니다.

## 결론: 이번 1차 제출에서 해야 할 일

**현재 노션의 11/15 작업 정의 기준으로, 실제 계산·정정이 동작하는 Mock 시연 영상을 준비하면 됩니다.** F03은 백엔드가 제공하는 Fixture와 순수 계산 로직을 화면에 연결하고, F04는 그 흐름을 안정적인 영상과 실행 안내로 전달하는 작업입니다.

영상에서는 `Mock 입력 → 계산 → 기록 조회 → 미확인 필드 → 사용자 금액 정정 → 재조회 → Reset`을 보여줍니다. 화면의 최종 숫자만 바꾸는 정적 목업으로 설명하지 않습니다. 현재 앱은 실제 이벤트를 처리해 결과를 만들고 정정 이력을 별도로 추가합니다.

**원격 서버 API·운영 DB·실차 SDK 연동은 이번 F03/F04 카드의 필수 조건으로 명시되어 있지 않습니다.** 여기서 백엔드와의 연결은 우선 공통 데이터 계약, 가상 이벤트, 순수 계산 결과를 맞추는 것입니다. 클라우드/서버 구성은 아직 확정되지 않은 영역입니다.

| 구분 | 이번 F03/F04 | 후속 제품 MVP |
| --- | --- | --- |
| 데이터 | 팀 B04의 명시된 Mock 이벤트 | 검증된 Pleos/차량 신호 |
| 계산·정정 | 실행되는 순수 로직·스토어·UI | 실제 차량 생명주기·영속 저장까지 통합 |
| 재실행 | 처음 상태에서 같은 데모를 재현 | 저장된 기록·정정 복구 및 중복 방지 |
| 입력 안전 | 시동 OFF를 쓰는 Mock 입력 잠금 | 주차와 플랫폼 UX 제한을 실제 API로 검증 |
| 영상 | Mock 표시, 생성→미확인→정정→재조회 | 실제 SDK와 검증 환경을 구분해 추가 증빙 |
| APK | 실제 release 빌드·실행 검증 시 선택 제출 | 지원 환경별 실제 실행·릴리즈 검증 |

이 결론은 **팀 노션의 현행 1차 작업 정의**에 근거합니다. 공모전 공식 접수양식과 최종 제출 조건은 B02/PM이 확인합니다. 문서의 작업 카드들은 초안·팀 합의 전 문구를 유지하고 있으므로, 기술 구현 성공을 팀 전체의 계약 승인으로 해석하지 않습니다.

## 기존 구현에서 확인한 부족한 부분과 보완

Antigravity의 기본 ICE 시나리오와 기존 F03 검사는 정상입니다. 다만 그 검사만으로 팀 B04의 예외·EV 시나리오까지 보장하지는 못했습니다. 팀 저장소의 실제 파일로 검사한 결과는 다음과 같습니다.

| 팀 Fixture | 기대 | 보완 전 | 보완 후 |
| --- | --- | --- | --- |
| F01 ICE 기본 | 12km / 35분 / 주유 후보 1 | 일치 | 일치 |
| F02 EV READY·충전 | 23km / 35분 / 충전 후보 1 | 구간·후보 생성 안 됨 | 일치 |
| F03 연료 소폭 흔들림 | 14km / 35분 / 후보 없음 | 기본 순서에서 일치 | 순서 변경을 포함해 일치 |
| F04 수집 공백 | 13km / 운행 20분 / 공백 10분 | 운행 30분, 공백 표시 데이터 없음 | 일치 |
| F05 중복 입력 | F01과 동일한 12km / 35분 | 12km / **30분** | 일치 |
| F06 EV 짧은 정차 | 18km / 35분 / 후보 없음 | 구간 생성 안 됨 | 일치 |

보완 사항:

- 같은 이벤트 ID와 같은 관측의 재수신을 한 번만 계산합니다. 이미 ON인 상태에서 ON을 다시 받아도 구간 시작 시각을 덮어쓰지 않습니다.
- 같은 시각의 센서 읽기와 전원 전환은 입력 순서가 바뀌어도 결과가 같습니다. 원시 배열은 변경하지 않습니다.
- 명시적인 `mockFeed.samplingSec`가 있는 Fixture에서만 공백을 계산하고 운행시간에서 제외합니다. 일반적인 장시간 이벤트 간격을 임의로 공백으로 만들지 않습니다.
- EV READY/SOC를 추가 계산하고 배터리 순증량·충전기 과금량을 각각 null/UNKNOWN으로 둡니다.
- 0km인 누적 주행거리를 미확인과 혼동하지 않습니다. 충돌하는 같은 ID는 오류로 처리해 잘못된 값을 조용히 덮어쓰지 않습니다.
- 기본 UI 입력을 팀 저장소 F01에서 생성합니다. `expected`는 테스트에서만 사용하며 앱에 포함하지 않습니다.
- 재계산 뒤에도 금액 정정과 이전 UNKNOWN 값, 별도 UserCorrection, 사건 확인 대기 상태가 보존되는지 검사합니다.

`RecordEngine.js`와 TypeScript 진입점은 하나의 공통 계산 구현을 사용하도록 맞췄습니다. 기존 `verify-f03.js`는 변경하지 않았고 그대로 통과합니다.

6/6 Fixture의 전체 출력 모델이 기대값과 일치합니다. 추가로 3~44%p의 Mock 증가 임계값과 같은 시각 이벤트 역순을 조합한 **504개 변형**이 통과했습니다. 원본 불변, 전체 재전송, 정정 유지, Reset 후 재시연도 검사합니다.

**해석 주의:** 3%p 기본값, 공백 판정, EV 필드명은 B04의 Mock 시험 가정입니다. 실제 차량 정책이나 승인된 최종 팀 계약으로 채택한 것이 아닙니다. 화면 시연은 여전히 **ICE F01**이며 EV는 계산 검사만 추가했습니다.

## 팀 Android 앱과의 관계

팀 저장소에는 별도로 Kotlin/Compose·Room·Vehicle SDK를 사용하는 Android 앱이 있습니다. [README](https://github.com/Mybread2/pleos-care-log/blob/dd7d0e0c69648b086c52df0c82bdfcb539ae17be/README.md)에는 SDK/에뮬레이터 시험 및 release APK 실행 결과가 기록되어 있습니다. **이번 작업에서 그 Android 시험을 재실행하거나 APK를 검증한 것은 아닙니다.**

그 앱은 `SnapshotEntity`, `RefillRecordEntity`, `costWon`, `UNCONFIRMED` 등의 모델을 사용합니다. 이번 웹 Mock 계약의 `MockEvent`, `EnergyEvent.fields.amountKrw`, `UserCorrection`, `DETECTED_UNCONFIRMED`와 구조가 다릅니다. 원격 API 주소만 설정하면 같은 데이터가 바로 나오는 관계가 아닙니다. 실제 앱과 합칠 때는 데이터 매핑·정정 이력·생명주기·안전 조건을 별도 설계해야 합니다.

## 촬영 전에 남은 일

1. 최신 앱 새로고침 후 F04 가이드대로 실제 영상을 녹화합니다. 현재 산출물은 촬영 가능한 앱과 가이드이며, 최종 영상 파일은 아직 없습니다.
2. 정정 뒤 다른 화면으로 갔다 돌아와 65,000원/USER_INPUT이 유지되는 모습을 포함합니다.
3. 실행 환경을 브라우저 기반 Mock 프로토타입으로 적고, 실제 SDK·실차·영구 복구를 완료한 것으로 설명하지 않습니다.
4. PM에게 영상 링크, 소스 공유 링크 또는 소스 ZIP, 실행 안내를 전달합니다. 공유 링크 업로드/확인은 아직 수행하지 않았습니다.
5. APK를 선택 제출한다면 실제 Android release 빌드·서명·실행 근거를 별도로 확인합니다. HTML 번들은 APK가 아닙니다.

## 후속 단계의 미구현 범위

전체 제품 P0에서 요구하는 영구 저장·재실행 복구, Journey 경계 수정, 실제 권한/지원 안내, 실제 주차·Car UX 판정, Pleos SDK 통합, EV 사용자 화면은 이 웹 Mock의 완료 범위가 아닙니다. 이는 이번 핵심 Mock 영상의 계산 오류와 구분해 관리해야 합니다.

노션의 담당자/작업 상태나 팀 저장소 원격 브랜치는 이번 검토로 변경하지 않았습니다.
